## 1. หน่วยงานและสถานะ CII

พ.ร.บ.การรักษาความมั่นคงปลอดภัยไซเบอร์ พ.ศ.2562 (Cybersecurity Act) มีผล 28 พฤษภาคม 2562 กำหนดคณะกรรมการการรักษาความมั่นคงปลอดภัยไซเบอร์แห่งชาติ (กมช.; NCSC) คณะกรรมการกำกับดูแลด้านการรักษาความมั่นคงปลอดภัยไซเบอร์ (กกม.) และสำนักงานคณะกรรมการการรักษาความมั่นคงปลอดภัยไซเบอร์แห่งชาติ (สกมช.; NCSA) แยกผู้กำหนดนโยบาย ผู้ใช้อำนาจกำกับ และสำนักงานปฏิบัติ [รวมตัวบททางการ NCSA](https://drive.ncsa.or.th/s/FQk8f6My94Brcjc/download)

ม.49 ครอบคลุมภารกิจ/บริการด้านความมั่นคง บริการภาครัฐที่สำคัญ การเงิน/ธนาคาร IT/โทรคมนาคม ขนส่ง/โลจิสติกส์ พลังงาน/สาธารณูปโภค สาธารณสุข และด้านอื่นที่กำหนด **อยู่ในอุตสาหกรรมไม่เท่ากับได้รับกำหนดเป็น CII ทุกบริษัท** ต้องตรวจประกาศและการกำหนดรายหน่วยงาน

ประกาศ กมช. เรื่อง การกำหนด หลักเกณฑ์ ลักษณะหน่วยงานที่มีภารกิจหรือให้บริการเป็นหน่วยงานโครงสร้างพื้นฐานสำคัญทางสารสนเทศ และการมอบหมายการควบคุมและกำกับดูแล พ.ศ.2568 ประกาศ 16 กันยายน 2568 ปรับกรอบเดิมปี 2564 พิจารณาความสำคัญของบริการและผลกระทบเมื่อขัดข้อง และบทบาทผู้กำกับแต่ละด้าน ไม่ใช้เกณฑ์รายได้ของ DPS มาแทนการกำหนด CII [ราชกิจจาฯ](https://ratchakitcha.soc.go.th/documents/86191.pdf)

**ก่อนออกความเห็น:** ขอหนังสือ/รายชื่อกำหนดสถานะ ขอบเขตระบบสำคัญ หน่วยกำกับ และประมวลแนวปฏิบัติที่ลูกค้าใช้ หากไม่ชัด มีช่องวินิจฉัยตาม ม.51 การเป็นผู้ขายให้ CII ไม่ทำให้ผู้ขายเป็น CII โดยอัตโนมัติ แต่ผู้ขายอาจได้รับหน้าที่ตามสัญญาหรือคำสั่งที่ชอบด้วยกฎหมาย

## 2. หน้าที่และการรายงาน

| ฐาน | หน้าที่ที่ต้องแปลงเป็นหลักฐาน |
|---|---|
| ม.44 | รัฐ ผู้กำกับ และ CII จัดประมวลแนวทาง/กรอบมาตรฐานตามขอบเขต; ไม่ใช้ certificate แทนแผนรับมือ |
| ม.52 | แจ้งข้อมูลเจ้าของ/ผู้ครอบครอง/ผู้ดูแลระบบและการเปลี่ยนตามกฎหมาย |
| ม.53–54 | ผู้กำกับตรวจมาตรฐาน; CII ประเมินความเสี่ยงและตรวจสอบไซเบอร์โดยผู้ตรวจภายใน **หรือ**ผู้ตรวจอิสระภายนอกอย่างน้อยปีละหนึ่งครั้งตามตัวบท |
| ม.55–56 | แก้ช่องว่างตามที่ผู้กำกับตรวจพบ และร่วมกลไก/การทดสอบรับมือที่กฎหมายกำหนด |
| ม.57 | เหตุไซเบอร์ที่มีนัยสำคัญต่อระบบ CII ต้องรายงาน สกมช.และผู้กำกับตามหลักเกณฑ์รายงาน |
| ม.58 | รัฐ/CII ตรวจและประเมินเมื่อเกิดหรือคาดว่าจะเกิดภัย แล้วป้องกัน รับมือ ลดผลกระทบและแจ้งตามเงื่อนไข |

ประกาศ กกม. เรื่อง หลักเกณฑ์และวิธีการรายงานภัยคุกคามทางไซเบอร์ พ.ศ.2566 เป็นกฎประกอบการรายงาน ต้องใช้ฉบับและแบบปัจจุบัน รวมข้อกำกับรายอุตสาหกรรม ไม่คัดเส้นตาย PDPA มาแทนเวลารายงานไซเบอร์; การแจ้งผู้ขาย/ลูกค้าไม่แทนการแจ้งหน่วยงานโดยผู้มีหน้าที่

ทะเบียนเหตุควรแยก **เวลาตรวจพบ → เวลาประเมินนัยสำคัญ → ข้อมูลที่ทราบ → มาตรการ → ผู้แจ้ง/ผู้รับ → การเพิ่มเติม/ปิดเหตุ** ไม่รอ forensic report สุดท้ายก่อนประสานหน้าที่รายงาน และส่งเหตุละเมิดข้อมูลส่วนบุคคลไป `thai-pdpa`

## 3. ระดับภัยและอำนาจรัฐ

ม.60 แยก **ไม่ร้ายแรง / ร้ายแรง / วิกฤติ** จากผลต่อระบบสำคัญ การให้บริการ และผลระดับประเทศ ไม่ใช่ชื่อ severity ใน ticket ของบริษัทโดยอัตโนมัติ

ม.61–64 ให้กลไกรวบรวมข้อมูล/ช่วยเหลือ/ประสานและใช้อำนาจตามเงื่อนไขเมื่อร้ายแรง ม.65 วางอำนาจสั่งการเฉพาะจำเป็น เช่น เฝ้าระวัง ตรวจระบบ แก้ภัย และหยุดใช้ระบบตามฐานที่เกี่ยวข้อง ม.66 เกี่ยวกับตรวจสถานที่ เข้าถึง/ทดสอบระบบ และยึด/อายัด **อำนาจแทรกแซงบางชนิดต้องร้องศาล ไม่ใช่ทุกอำนาจได้รับยกเว้นศาล**

ม.67 วางบทบาทสภาความมั่นคงแห่งชาติในระดับวิกฤติ ม.68 กรณีจำเป็นเร่งด่วนและภัยระดับวิกฤติ ให้การมอบหมายดำเนินการทันทีเฉพาะจำเป็นก่อนร้องศาลตามเงื่อนไขและกลไกแจ้งศาล ไม่ขยายเป็นสิทธิประจำในการเข้าถึงข้อมูลเอกชนทั้งหมด ม.69–70 คุ้มครองข้อมูลที่ได้มาจากการใช้อำนาจและกรณีเปิดเผยโดยมิชอบ/ประมาทตามตัวบท

ผู้รับคำขอตรวจ **ระดับภัย → ผู้สั่ง/การมอบหมาย → อำนาจที่ใช้ → ศาลเมื่อจำเป็น → ระบบ/ช่วงเวลา → การรักษาหลักฐาน/ความลับ**; แยกจาก ม.18–20 พ.ร.บ.คอมพิวเตอร์ฯ ใช้ SOP ใน `content_and_request_operations.md`

## 4. มาตรฐานคลาวด์และเว็บไซต์

| มาตรฐาน | วันและขอบเขต | งานที่ต้องทำ |
|---|---|---|
| ประกาศ กมช. เรื่อง มาตรฐานด้านการรักษาความมั่นคงปลอดภัยไซเบอร์ระบบคลาวด์ พ.ศ.2567 | มีผล **10 กันยายน 2569 (2026)**; การใช้คลาวด์สาธารณะของรัฐ ผู้กำกับ และ CII กับผู้ให้บริการตามขอบเขต ไม่ใช่ SaaS ทุกบริษัทต้องรับใบอนุญาตคลาวด์ | CSC/CSP shared responsibility การประเมินความเสี่ยง ชั้นข้อมูล ขอบเขตการรับรอง ข้อควบคุมและหลักฐานตามบริการจริง |
| ประกาศ กมช. เรื่อง มาตรฐานการรักษาความมั่นคงปลอดภัยสำหรับเว็บไซต์ พ.ศ.2568 | ลงนาม 10 กันยายน ประกาศ 16 กันยายน 2568; มีผล **16 กันยายน 2569**; รัฐ ผู้กำกับ CII ต้องปฏิบัติ ภาคเอกชนทั่วไปเป็นการส่งเสริม | ครอบคลุม website/web/database server ทั้ง on-premises/cloud/hosting ประเมินผลกระทบและใช้ข้อควบคุมตามระดับ |

[ศูนย์มาตรฐานคลาวด์ NCSA](https://cloudsecurity.ncsa.or.th/) · [เว็บไซต์: ขอบเขต](https://websitesecurity.ncsa.or.th/target.html) · [FAQ ทางการ](https://websitesecurity.ncsa.or.th/faq.html) · [ต้นฉบับเว็บไซต์](https://ratchakitcha.soc.go.th/documents/86192.pdf)

เว็บไซต์ต้องประเมินตนเองอย่างน้อยปีละหนึ่งครั้งและเมื่อเปลี่ยนระบบสำคัญ; ระดับต่ำ/กลางเสนอต่อผู้บริหารและเก็บหลักฐาน ระดับสูงส่งตามช่องทางผู้กำกับ/สกมช.ที่กำหนด จัดรายการแก้ไขและเจ้าของงานตามแบบ ค1/ค2 การได้ ISO/IEC 27001 ไม่ยกเว้นทั้งหมด ต้องตรวจ scope และส่วนที่ยังไม่ครอบคลุม ไม่กำหนด technical control ทุกข้อให้ทุกระดับโดยไม่มี mapping

แยกมาตรฐานที่มีผลแล้วจาก **แผนบูรณาการคลาวด์ 2569–2573** ซึ่งเป็นแผนขับเคลื่อน เป้าหมายในแผนไม่ใช่หน้าที่ใหม่ของผู้ขายทุกคน ระบบลูกค้าอยู่บน hosting ไม่ทำให้เจ้าของเว็บไซต์พ้นหน้าที่ จึงต้องส่งต่อข้อควบคุมผ่านสัญญาโดยระบุว่าใครทำอะไร

## 5. Cloud First และชั้นข้อมูล

ในการจัดซื้อรัฐ ตรวจนโยบายการใช้คลาวด์เป็นหลัก (Cloud First) แนวทางจัดชั้นข้อมูล และ TOR ของลูกค้าควบคู่มาตรฐาน NCSA ขอรายการชุดข้อมูลและระดับตามกรอบหน่วยงานจริง ไม่ตั้งว่า “ข้อมูลภาครัฐทุกประเภทต้องอยู่ไทย” หรือ “ใช้ public cloud ได้ทั้งหมด” โดยไม่มีข้อกำหนดเฉพาะ

ทำตาราง **ข้อมูล/เจ้าของ → ระดับ/เหตุผล → ระบบและสถานที่ประมวลผล → access/key management → backup/DR → ผู้รับจ้างช่วง → การโอน/คืน/ลบ → กฎหรือ TOR ที่รองรับ** แนวทางธรรมาภิบาลข้อมูลและการจัดชั้นต้องตรวจฉบับ DGA/คณะกรรมการและมติที่หน่วยงานอ้าง ไม่ถือคำแนะนำหรือ roadmap แทนประกาศกำหนดเขตข้อมูล และส่ง PDPA ไป `thai-pdpa`

## 6. Vendor readiness และตัวอย่าง

| หัวข้อ | หลักฐานก่อนผูกพันสัญญา |
|---|---|
| Scope | ระบบสำคัญ บริการที่จัดซื้อ หนังสือ CII ชั้นข้อมูลและข้อควบคุมที่ใช้ |
| Shared responsibility | ตารางงาน CSC/CSP และผู้รับจ้างช่วง; ไม่ทิ้งงาน monitoring/patching ไว้ระหว่างคู่สัญญา |
| Access/security | สิทธิ admin การอนุมัติ remote support isolation encryption/key roles และหลักฐาน log |
| Incident | ช่องติดต่อ การยกระดับ เหตุเริ่มและเวลาสัญญาที่ช่วยลูกค้าปฏิบัติหน้าที่กฎหมาย; ไม่อ้างเวลาสัญญาเป็นเวลาตามกฎหมาย |
| Resilience | backup/restore การทดสอบ DR เป้าหมายบริการและเงื่อนไขจริง ไม่รับรอง uptime ไร้ข้อยกเว้น |
| Audit/exit | หลักฐานตรวจรับ สิทธิ audit ที่สมเหตุสมผล การแก้ข้อบกพร่อง การส่งออก/คืน/ลบและ legal hold |

**ตัวอย่างสมมุติ:** ผู้ขาย SaaS เสนอโรงพยาบาลที่เป็น CII → ขอขอบเขตระบบ/หนังสือกำหนดมาตรฐาน ทำ gap matrix และ security schedule ไม่ประกาศว่าผู้ขายเป็น CII ทั้งบริษัท แจ้งช่องว่างที่แก้ได้ก่อนรับข้อมูลจริงและกำหนดผู้รับผิดชอบทั้งสองฝ่าย แม่แบบข้อสัญญาใน `templates.md`; เงื่อนไขทั่วไปส่ง `thai-contract-master`

## หลักการ

สถานะ CII ต้องมีหลักฐาน; ภายใน **หรือ**ภายนอกตาม ม.54 ไม่ใช่ต้องทำทั้งสองทุกปี; มาตรฐานปี 2567/2568 มีผลปี 2569 ตามวันของแต่ละฉบับ; กฎโดยตรง สัญญา และแนวทางสมัครใจต้องแยก; ภัยวิกฤติไม่ใช่อำนาจไร้ขอบเขต
