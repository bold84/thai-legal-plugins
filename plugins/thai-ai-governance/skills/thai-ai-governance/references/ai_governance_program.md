# ai_governance_program.md — ระบบกำกับ AI ตลอดวงจรและหลักฐานการตัดสินใจ

อ่านไฟล์นี้เมื่อวาง governance ประเมินก่อนเปิดบริการ ตรวจ shadow AI ผู้ขายหรือเหตุ

ข้อมูล ณ 9 ตุลาคม 2569 (2026) — **ข้อเสนอองค์กร** อิง ETDA [G3–G4], ธปท./คปภ.ใน scope [G5–G6] และแนวทาง PDPC [G12] ไม่ใช่หน้าที่ร่าง AI ที่มีผลแล้ว รหัสใน `key_sections.md`

## สารบัญ
1. เจ้าของและประตูอนุมัติ
2. ทะเบียนและบทบาท
3. ความเสี่ยงและความพร้อมต่อร่าง
4. ทดสอบและมนุษย์กำกับ

6. เหตุการณ์และการทบทวน
7. ตัวอย่างการใช้จริง

## 1. เจ้าของและประตูอนุมัติ

ETDA: **AI Governance Structure -> AI Strategy -> AI Operation** (สรุปสาระ) ใช้โครงสร้างที่มีได้ แต่ต้องมีผู้ตัดสินใจจริง [G3]

| ผู้รับผิดชอบ | หลักฐานที่ต้องมี |
|---|---|
| ผู้บริหาร/ผู้อนุมัติความเสี่ยง | นโยบาย risk appetite เงื่อนไขเปิด/ระงับ ผู้รับความเสี่ยงที่เหลือ |
| เจ้าของบริการ | วัตถุประสงค์ ขอบเขตใช้ ผู้ได้รับผลกระทบและช่องทางร้องเรียน |
| เจ้าของโมเดล/เทคนิค | รุ่น ข้อมูล/สิทธิ ผลทดสอบ change log rollback และ stop control |
| กฎหมาย/ข้อมูล/ความปลอดภัย | legal map PDPA/IP/security findings และเงื่อนไขที่ยังไม่ผ่าน |
| ผู้ตรวจอิสระตามสัดส่วนความเสี่ยง | ตรวจหลักฐาน ไม่ให้ผู้พัฒนารับรองตนเองทั้งหมด |

Gate: **เริ่ม -> ข้อมูล/ผู้ขาย -> ทดสอบ -> เปิด -> เปลี่ยนสำคัญ -> เลิก** มีผู้ลงนาม หลักฐาน เงื่อนไข/อายุข้อยกเว้น งานกระทบสิทธิ/สุขภาพ/เงินมากยกระดับผู้อนุมัติ

## 2. ทะเบียนและบทบาท

ทะเบียนรวมโมเดลเอง API, agent, RAG, SaaS/extension และเครื่องมือพนักงาน ใช้แบบ `templates.md` ต่อระบบ/รุ่น/use case ไม่ใช่รายชื่อผู้ขาย

Role map: ผู้พัฒนา ขายภายใต้ชื่อตน กำหนดงานใช้ เผยแพร่ แพลตฟอร์ม; มีหลายบทบาทได้ PDPA controller/processor ประเมินแยกจาก provider/deployer

Shadow AI: สำรวจบัญชี/extension/SaaS AI จัดเครื่องมืออนุมัติ ห้าม/ช่องขอใช้และทางเลือก ไม่ลงข้อมูลลับ/อ่อนไหวในเครื่องมือไม่ผ่าน ฝึก **AI literacy** ตรวจข้อจำกัด/อ้างอิงและแจ้งเหตุ ไม่ติดตามพนักงานเกินจำเป็น [G4, G12]

## 3. ความเสี่ยงและความพร้อมต่อร่าง

ประเมินผลเสีย โอกาส ขนาด/ความเปราะบาง ย้อนกลับได้หรือไม่และทางเลือกไม่ใช้ AI; บันทึก **inherent -> control -> residual risk** ไม่แต่งคะแนนกฎหมาย

| คำถาม | ผล readiness ไม่ใช่คำตัดสินกฎหมาย |
|---|---|
| ชักจูงแฝงเร้น/เลือกปฏิบัติเข้าถึงสิทธิ? | หยุดให้กฎหมายตรวจ; เทียบแนวต้องห้าม/เสี่ยงร้ายแรงของร่าง |
| เข้าลักษณะความปลอดภัยสาธารณะ/การเงิน/การค้า? | เฝ้ารายการจดแจ้ง-ขึ้นทะเบียน-อนุญาต อย่าออกใบอนุญาตสมมติ |
| กระทบสุขภาพ ความมั่นคง พลังงาน โทรคมนาคม ขนส่ง/สาธารณูปโภค? | เตรียมหลักฐานมาตรการเสี่ยงสูง; ไม่ถือว่าทุกระบบในภาคเป็น high-risk |
| สร้าง/ดัดแปลงเนื้อหาที่คนอาจเชื่อว่าเป็นจริง? | เตรียมป้าย/marker ผู้เผยแพร่และแพลตฟอร์ม แยกจากระดับความเสี่ยง |
| ผู้ซื้อรัฐ/CII? | ตรวจ TOR กฎหมายปัจจุบันและ readiness สัญญาควบคุม/ที่ตั้งข้อมูล |

ใช้ `draft_ai_act_2026.md` ประกอบ PDF ทางการ [D11] ระบบไม่เข้ากลุ่มร่างยังต้องตรวจ PDPA โฆษณา สิทธิ ความลับและสัญญา; ระยะเก็บตามร่างเฉพาะระบบ/บทบาทนั้นไม่ใช้เป็นระยะทุกระบบวันนี้

## 4. ทดสอบและมนุษย์กำกับ

ก่อนเปิด: นิยามผลดี/เสีย เกณฑ์รับตามงาน ชุดข้อมูลมีสิทธิ คนทดสอบ/ผลแยกกลุ่ม ภาษาไทย/สำเนียง ความกำกวม/ข้อมูลขาด OOD, hallucination/bias, jailbreak/prompt injection, leakage และ agent tools ไม่ใช้ benchmark vendor แทนงานจริง [G4–G6]

เก็บ test case รุ่น/ตั้งค่า expected/actual severity/แก้ไข งานอันตรายต้องพิสูจน์ขอบป้องกัน ไม่ตั้ง accuracy เดียวทุกระบบ ใช้ข้อมูลสังเคราะห์/อนุมัติ

| การกำกับ | ต้องพิสูจน์ |
|---|---|
| Human-in-the-loop | คนเห็นข้อมูลเพียงพอ ตรวจทุกการตัดสินใจสำคัญก่อนเกิดผล และ override ได้ |
| Human-over-the-loop | มี monitoring/threshold ที่งานกำหนด คนรับ alert และหยุด/ย้อนกลับได้ทัน |
| อัตโนมัติภายใต้ขอบเขต | เหตุผลที่ยอมรับได้ จำกัดสิทธิ/การทำรายการ และ fallback ไม่ทำให้ความเสี่ยงเพิ่ม |

ผู้ตรวจต้องมีทักษะ เวลา อำนาจและไม่ถูก KPI บังคับเชื่อ AI ระบุงานห้ามตัดสินลำพัง/ช่องทบทวนตามกฎหมายหรือนโยบาย ไม่ใช่แค่คนกดอนุมัติ

## 5. ความโปร่งใส ข้อมูลและผู้ขาย

- **เปิดเผย:** บทบาท AI ข้อจำกัด ผู้รับผิดชอบ/ติดต่อ ป้ายเห็น/ฟังได้ร่วม provenance/metadata
- **ข้อมูล:** แยก training/RAG/inference/log/evaluation, flow/สิทธิ/ที่ตั้ง/ลบ ส่ง PDPA/IP; public ไม่แปลว่าใช้ได้ทุกงาน
- **ผู้ขาย:** no-training รุ่น ผู้รับช่วง ที่ตั้ง/support retention ผลทดสอบและ incident ตรวจสัญญา/ค่าตั้งจริง [G4–G6, G12]
- **เปลี่ยน:** โมเดล ข้อมูล prompt/tool สิทธิ agent/งานเปลี่ยนประเมินใหม่; silent update มีแจ้ง/rollback/exit ไม่ freeze แล้วละเลยช่องโหว่
- **บันทึก:** เท่าจำเป็นตามฐานกฎหมาย/สัญญา access/redact/legal hold ไม่ใช้ระยะร่างเป็นหน้าที่วันนี้

## 6. เหตุการณ์และการทบทวน

รับแจ้ง -> triage -> จำกัด/หยุด -> เก็บหลักฐาน -> กฎหมาย/แจ้ง -> แก้/ทดสอบ -> อนุมัติกลับ -> root cause/control แยก AI incident กับ data breach แต่ประเมินพร้อมกัน [G4–G6, G12]

ทีมเหตุ: owner เทคนิค กฎหมาย vendor/สื่อสาร ช่องเร่งด่วน เก็บ awareness รุ่น input/output จำเป็น กลุ่มกระทบ/การหยุด/ร้องเรียน ไม่เผยข้อมูลทั้งหมดในรายงานทั่วไป

แจ้งตามกฎหมายรายภาค/PDPA/สัญญาวันนี้; รายงานเหตุร่างยังไม่ใช้ ไม่มีเส้นตาย AI สากล breach ส่ง `thai-pdpa`, ไซเบอร์/CII ส่ง `thai-tech-platform-law`

ติดตาม error/ร้องเรียน/drift/override/เหตุ ไม่เฉพาะ uptime ทบทวนเมื่อเปลี่ยนงาน/รุ่น/vendor/กฎหมาย เลิกใช้ปิด endpoint/สิทธิ คืน/ลบตามสัญญา แจ้งผู้ใช้และเก็บหลักฐานจำเป็น

## 7. ตัวอย่างการใช้จริง

**สรุปเอกสารภายใน:** เน้นความลับ/ข้อมูล/hallucination ไม่ high-risk อัตโนมัติ ใช้เครื่องมืออนุมัติ no-training/คนตรวจต้นฉบับ

**สินเชื่อ:** ตรวจ ธปท. ข้อมูล/อคติ ผลลูกค้า คนทบทวนข้อยกเว้น/ร้องเรียน ไม่เรียกสิทธิ PDPA แบบ GDPR โดยไม่ตรวจฐาน [G5]

**สื่อ AI:** rights/claims review ก่อนเผยแพร่ ทดสอบป้ายที่ปลายทาง/ทางถอดแก้ ป้ายไม่แก้สิทธิใบหน้า/เสียงหรือโฆษณาเท็จ

## หลักการ

- มาตรการทุกตัวต้องมีเจ้าของ หลักฐานและเงื่อนไขใช้ ไม่สร้างนโยบายที่ไม่มีการปฏิบัติ
- แยกข้อเสนอองค์กรจากหน้าที่ที่ใช้บังคับและ readiness ตามร่าง
- เอกสาร final go/no-go ต้องให้ผู้มีอำนาจและทนายตรวจ พร้อมข้อสังเกตจากทนาย
