## 1. จับคู่บทบาทใน SaaS

ทดสอบรายกิจกรรมตาม ม.6/40 ไม่ใช้คำว่า vendor/customer แทนบทบาท ไม่ถือว่าเพียงชื่อ DPA ทำให้ทุกกิจกรรมเป็นการประมวลผลตามคำสั่ง

| กิจกรรม | บทบาทที่ต้องทดสอบ | หลักฐาน/งาน |
|---|---|---|
| tenant content | processor ถ้าทำตามคำสั่งลูกค้า | DPA ม.40 วรรคสาม; tenant isolation/คำสั่ง/สิทธิผู้ดูแล |
| บัญชี/เรียกเก็บเงิน | controller ถ้ากำหนด purpose เอง | notice/ฐาน; ม.24(3) ต้องเจ้าของข้อมูลเป็นคู่สัญญา ไม่ใช่พนักงานของลูกค้านิติบุคคลทุกคน |
| telemetry/analytics | own purpose → controller; ตามคำสั่ง → processor | แยกเนื้อหาลูกค้า ระบุตัวได้หรือไม่ ฐาน/retention/notice และ ม.21 |
| security log/support | อาจ processor หรือ controller แล้วแต่อำนาจจริง | ไม่เปลี่ยนบทบาทอัตโนมัติเพราะเรียกว่า security; จำกัดสิทธิ/audit trail |
| cloud/model sub-processor | ตามคำสั่งจริง → processor ช่วง | ประเทศ ผู้รับ support การอนุญาต/flow-down และโอนต่อ |
| ใช้เนื้อหาลูกค้าฝึกโมเดลเพื่อตน | controller ของกิจกรรมนั้น | ม.40 วรรคสอง; ฐาน/วัตถุประสงค์/notice ใหม่ ไม่ใช่สิทธิที่เกิดจาก DPA เอง |

การทำให้ไม่ระบุตัวก่อน analytics เป็นทางลดความเสี่ยง ไม่ใช่หน้าที่ anonymise ทุกกิจกรรมโดยไม่มีทางใช้ฐานอื่น; ต้องมีฐาน/คำสั่งสำหรับขั้นทำให้ไม่ระบุตัวด้วย ม.23(4) แจ้งประเภทผู้รับ ไม่ถือว่าการมีสัญญาลูกค้าแทนการแจ้งเจ้าของข้อมูลได้ โทษต้องตรงบทบาท/องค์ประกอบ ม.82–87 ไม่สรุปว่าการฝึกโมเดลทุกแบบปรับ 3 ล้านบาท

## 2. Logs, telemetry, BYOK

- **BYOK สองความหมาย:** กุญแจเข้ารหัสที่ผู้ให้บริการถอดไม่ได้ ต่างจาก API key ที่ใช้บัญชีโมเดลของลูกค้า; แบบหลังยังส่ง plaintext ไปผู้ให้บริการตาม flow จริง
- **ข้อยกเว้นนิยามการโอน:** ประกาศ ม.28/29 ข้อ 3 ไม่รวม transit/storage ที่บุคคลภายนอกเข้าถึงไม่ได้นอกจากผู้ส่ง/บุคลากร เพราะมาตรการเทคนิคหรือกฎหมายรองรับ ตรวจ support/ops/break-glass และ metadata ที่ระบุตัวได้ก่อนสรุป ไม่ใช้คำว่า BYOK รับรองข้อยกเว้น
- **มุม EU:** EDPB UC1/2 อาจรองรับ encryption/pseudonymisation ที่ได้ผลตามเงื่อนไข; UC6/7 กรณีต้องใช้ plaintext และกฎหมายปลายทางมีปัญหาไม่แก้ได้เพียงสัญญา ดู `cross_border_transfers_and_tia.md` ข้อ 6
- **Retention:** แยก log ที่กฎหมายบังคับจาก analytics/support; พ.ร.บ.คอมพิวเตอร์ฯ ม.26 จราจร ≥90 วัน สั่งเฉพาะราย/คราวไม่เกิน 2 ปี; ข้อมูลระบุผู้ใช้ ≥90 วันหลังสิ้นบริการ เฉพาะระบบที่เข้าเกณฑ์ → `thai-tech-platform-law` ฐาน ม.24(6)/ข้อยกเว้นลบ ม.33 ใช้เฉพาะส่วนจำเป็นตามกฎหมาย ไม่ครอบคลุมการเก็บทุก prompt ตลอดไป
- **ลบ:** ประกาศ พ.ศ. 2567 ข้อ 3–9 ครอบคลุมสำเนา/สำรอง; beyond use ไม่ใช่ลบจริงหรือข้อยกเว้นถาวร การทำไม่ระบุตัวต้องลดการระบุตัวทางอ้อม/กันเชื่อมกลับ ไม่ใช้ hash อย่างเดียว

(แนวปฏิบัติ) ตารางระบบควรมี `ข้อมูล | purpose | role/base | retention | ประเทศ/ผู้เข้าถึง | วิธีลบ/restore | หลักฐาน` ทดสอบว่าการกู้ backup นำข้อมูลที่ลบกลับมาใช้หรือไม่ ไม่ใช้การเข้ารหัสเป็นหลักฐานว่าไม่เกิดเหตุเสี่ยงโดยไม่ตรวจการเข้าถึงกุญแจ

## 3. AI: prompt, ฝึกโมเดล, endpoint ต่างประเทศ

**แนวทาง AI ฉบับทางการ:** สคส.เผยแพร่ “แนวทางการดำเนินการด้านการคุ้มครองข้อมูลส่วนบุคคลเกี่ยวกับการพัฒนาและการใช้งานเทคโนโลยีปัญญาประดิษฐ์ (Artificial Intelligence)” version 1.0 ใน ต.ค. 2569; [PDF ทางการ](https://www.pdpc.or.th/wp-content/uploads/2026/10/-2.pdf) หน้า 4 ระบุเป็นคำแนะนำ ไม่มีสภาพบังคับ/ไม่ผูกพันการพิจารณาความผิด จึงไม่ใช้ร่าง ก.พ. 2569 แทนฉบับปัจจุบัน และไม่อ้างเป็นพระราชบัญญัติ AI

ตัวบทไทยไม่มีบท DPIA/ADM/joint controllers โดยเฉพาะแบบ GDPR; หน้าที่ PDPA ทั่วไปยังใช้ครบ การจัด LIA/DPIA, input/output guardrails, human review และ machine unlearning ตามแนวทางเป็นวิธีบริหารความเสี่ยง ไม่ใช่สิทธิ/บทลงโทษใหม่ที่แนวทางสร้างขึ้น

| ขั้น | ประเด็นกฎหมาย/เงื่อนไข | มาตรการเสนอ |
|---|---|---|
| prompt/RAG/output | ม.6: อาจระบุตัวได้ รวม embeddings; เก็บ/ใช้/เปิดเผยต้องฐาน ม.24/26 และ notice | ลด/ปิดข้อมูลส่วนบุคคล จำกัด retrieval/สิทธิ agent และตรวจ output |
| training/fine-tuning | คำสั่ง processor + ฐานของ controller; own use ต้องประเมินบทบาทและ ม.21; purpose ใหม่แจ้ง/ยินยอมเว้นกฎหมาย | no-training เป็นค่าตั้งต้นตามสัญญา แยกคำสั่ง/การอนุมัติจาก consent เจ้าของ |
| public dataset/scraping | ม.25 แจ้งไม่ชักช้า ≤30 วัน/ครั้งแรกตามเงื่อนไข; ข้อยกเว้นต้องพิสูจน์; ข้อมูลอ่อนไหวไม่ใช้ ม.24(5) แทน ม.26 | ทำแหล่งที่มา ฐานและข้อจำกัดสิทธิ; “อยู่บนเว็บ” ไม่พอ |
| foreign endpoint/support | เปิดเผยแก่ผู้รับต่างประเทศตามนิยาม → ม.28–29; role/DPA และ onward flow แยก | region pinning, no-training/retention, รายชื่อผู้รับและเครื่องมือโอน |
| สิทธิ/ลบ | คำขอเข้าถึง 30 วัน/ขยายตามประกาศ; ลบ ≤90 วันตามเงื่อนไข ไม่ใช่ทุกสิทธิ 30 วัน | data lineage ครอบคลุม dataset/vector/cache/output และประเมินว่า weights ยังระบุตัวได้หรือไม่ |
| leakage/เหตุละเมิด | ม.37(4)/40(2), ประกาศแจ้งเหตุ พ.ศ. 2565 | ตรวจเหตุ/ความเสี่ยง บันทึก awareness แจ้งไม่ชักช้า ไม่รอผลสอบสวนสุดท้าย |

ข้อจำกัด unlearning ไม่ยกเว้นหน้าที่; ตรวจวิธีลบ/ทำให้ข้อมูลใช้ไม่ได้ตามประกาศและผลต่อเจ้าของข้อมูล ไม่สั่ง “ลบ model weights ทุกกรณี” โดยไม่ประเมินข้อมูลจริง หากจะใช้ข้อมูลฝึกหรือ output ในเรื่องลิขสิทธิ์/การกำกับ AI ให้ส่งต่อสกิลตรงเรื่อง

## 4. งานสองระบอบ GDPR + PDPA

แยก **ขอบเขต Art.3**, **หน้าที่ตามสัญญา Art.28**, และ **Chapter V ของการโอน** — บริษัทไทยมีลูกค้า EU ไม่ทำให้ทุกการประมวลผลอยู่ใต้ GDPR เอง ขณะ processor ที่อยู่ไทยเข้า PDPA ม.5 วรรคหนึ่งแม้ข้อมูลต่างชาติ

| กรณี | ผล/งาน |
|---|---|
| B2B ไทยประมวลผลให้ลูกค้า EU | ตรวจ Art.3 แยก; ลูกค้าทำ Art.28 contract/เครื่องมือโอน ปกติ SCC Module 2 (C→P) หรือ 3 (P→P) ตามบทบาทจริง |
| บริษัทไทยเสนอแก่คนใน EU/monitor พฤติกรรมใน EU | Art.3(2) ตามเงื่อนไข; ตรวจตัวแทน Art.27/ข้อยกเว้น ROPA Art.30 DPO Art.37 ไม่ถือว่าทั้งหมดต้อง DPO โดยอัตโนมัติ |
| ประมวลผลในบริบท establishment EU | Art.3(1) ตามบริบท/กิจกรรม ไม่ใช่ทุกข้อมูลของกลุ่ม; EU→ไทยยังตรวจ Chapter V |
| ผู้รับไทยเองอยู่ใต้ GDPR สำหรับ processing ที่รับ | Decision 2021/914 Art.1(1) จำกัด SCC ชุดนี้สำหรับ processing ของผู้รับที่ไม่อยู่ใต้ GDPR; EC ยังพัฒนาชุดเพิ่ม ไม่รับรองกำหนดอนาคต ต้องตรวจเครื่องมือที่ใช้ได้ก่อนโอน |
| ไทยส่งต่อไป model endpoint/ผู้รับอื่น | ม.28–29 ของฝั่งไทย และข้อกำหนด onward ของผู้ส่ง EU/SCC ต้องครบ; ASEAN MCC ไม่ใช่ GDPR Art.46 tool เอง |
| คำสั่งรัฐไทยขอข้อมูลจาก EU | GDPR Art.48 ไม่ให้คำสั่งต่างประเทศเป็นฐานโอนเอง; ตรวจฐาน/เครื่องมือ/ข้อ 15 SCC และกฎหมายความลับไทย → TIA ข้อ 4–5 |

**ตารางปฏิบัติร่วม (การวิเคราะห์):**
- DPA รวม ม.40 และ Art.28(3) เมื่อเกี่ยวข้อง พร้อม annex purpose/data/duration/TOMs/sub-processors; การรับสัญญา EU ไม่ยกหน้าที่ไทย
- Processor ไทยแจ้ง controller ไม่ชักช้าภายใน 72 ชั่วโมงนับทราบเท่าที่ทำได้; GDPR Art.33(2)/SCC Module 2 ข้อ 8.6(c) คือ without undue delay ไม่ใช่สิทธิรอ 72 ชั่วโมง เลือกสัญญาให้ผู้ควบคุมทันทั้งสองนาฬิกา
- Controller ที่มีหน้าที่สองฝั่งแจ้ง สคส./EU authority แยก ไม่ถือว่าแจ้งที่หนึ่งแทนอีกที่หนึ่งได้; high-risk subject notice ตาม ม.37(4)/Art.34 ตรวจข้อยกเว้นแต่ละระบอบ
- ROPA หนึ่งระบบทำได้แต่แสดงรายการ ม.39/40 และ Art.30 ครบ; DPO/ตัวแทนแต่งตั้งตามเกณฑ์แต่ละฝ่าย ไม่ใช้ผู้แทน EU แทนไทย
- DSAR ไทยใช้ ม.30/ประกาศ พ.ศ. 2569; GDPR Art.12(3) ใช้หนึ่งเดือนและเงื่อนไขขยายต่างกัน ไม่ทำ SLA “30 วันทุกสิทธิทั้งสองฝั่ง”
- DPIA/ADM/joint controller เทียบ Art.35/22/26 เมื่อ GDPR ใช้; ไม่ทำให้กลายเป็นบท PDPA ไทย ตรวจร่างแก้ EU/ไทยก่อนงานใหม่

แหล่ง: GDPR/Decision ใน `key_sections.md` ข้อ 1/4; EDPB Guidelines 3/2018 และ 05/2021/02/2024 และ EC SCC guidance ในรายการแหล่งที่มา

## 5. จุดเสี่ยงและตัวอย่าง

จุดเสี่ยง: security logs = controller ทุกครั้ง; B2B contract = ฐานสัญญาของทุกคน; embeddings = นิรนาม; API key = encryption; เรียกทุก DSAR ว่า 30 วัน; ASEAN MCC แทน SCC ฝั่ง EU; ฉบับ AI ปัจจุบันยังเป็นร่าง

(การวิเคราะห์) บริษัทบริการลูกค้าใช้ RAG สรุป tickets: แยก vendor processor ของ tickets กับ own analytics controller; ตรวจข้อมูลสุขภาพที่ปะปน คำสั่ง no-training/retention และผู้รับ API ต่างประเทศ ก่อนส่งจริงให้ผ่านฐาน/notice/DPA/เครื่องมือโอนและมีทางค้น/ลบ dataset/vector/cache ของ tenant ได้ ปิดชื่อไม่ได้แปลว่านิรนามถ้ายังเชื่อมกลับได้

## หลักการ
- จับคู่บทบาทตามกิจกรรม/อำนาจจริง; BYOK ไม่ใช่ข้อยกเว้นสำเร็จรูป

- ปิดท้ายด้วย "ข้อสังเกตจากทนาย"
